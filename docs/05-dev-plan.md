# GachaNote 开发计划

2026-10-24 · Can

## 1. 计划说明

本计划把《功能需求》的 F-01–F-24 和《架构设计》拆成可执行的任务，按里程碑推进。

### 1.1 前提

- 个人项目，一人开发，业余时间推进；Claude 可协助编码和评审。
- 桌面端只做 Windows；移动端和服务器不在 v0.3 之前的范围内。
- UI/UX 与原型仍可能调整，所以前端页面任务排在核心层之后，给设计留出修改时间。

### 1.2 划分原则

- **先底层后界面**：统计口径是产品的核心，先把 `core`、`formats`、`store` 做到有测试保障，再接前端。
- **先一款游戏走通全链路**：以原神为样板（格式最成熟、参考项目最多），导入 → 统计 → 展示跑通后再铺开其余五款。
- **每个里程碑都可用**：结束时主分支能构建、测试全绿，功能在应用里能实际使用。

### 1.3 规模口径

任务规模用专注工作时间估算，不换算成日历日期：**S** ≤ 1 天，**M** 2–4 天，**L** 1–2 周。暂不排日历日期，按里程碑顺序推进；需要时再按每周投入时间换算。

### 5.2 后续方向（不排期）

- **移动端**：新建 Tauri mobile 外壳，复用全部 crate；移动端无法读游戏缓存，导入以文件和手动粘贴 URL 为主。前端按断点切到底部导航。
- **服务器与同步**：新增一个远程 `RecordRepository` 实现和一个 axum 服务端外壳；UUID v7 主键与去重键保证多端合并不冲突。
- **更多游戏**：按插件接口新增，必要时新增 `Mechanic` 变体。

## 7. 风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 官方接口或缓存格式变化 | URL / token 拉取失效 | 拉取器独立成插件，可单独发修复版；文件导入始终可用作兜底；关注参考项目的更新 |
| 卡池规则参数不准或游戏调整机制 | 预测与欧非评价偏差 | 参数放在规则模板且可被元数据包覆盖；待确认参数在界面标注「估算」 |
| 元数据包维护工作量大 | 新卡池 UP 判定变成估算 | 缺数据时退化为「常驻名单之外即 UP」；接受社区 PR；CI 自动校验 Schema |
| 鹰角接口没有公开文档 | v0.2 token 拉取延期 | 放在 v0.2，不阻塞 v0.1；只参考行为不复制代码 |
| 未签名安装包被 SmartScreen 拦截 | 新用户顾虑 | README 说明；发布页公开 SHA-256；用户量上来后评估证书 |
| 用户数据损坏或误删 | 记录丢失（官方只保留半年到一年） | 单事务导入、自动备份 5 份、迁移前备份；提示用户定期导出 UIGF / GNJ |
| 业余开发进度不稳定 | 版本拖延 | 每个里程碑都可用；必要时把 P1/P2 功能顺延，不压缩测试 |

## 8. 工作方式

- **分支**：`main` 始终可构建；每个任务一个分支（如 `feat/T-15-stats-engine`），通过 PR 合并，squash merge。
- **看板**：用一个 GitHub Projects 看板跟踪，每个 T 编号一张卡片，列为「待办 / 进行中 / 评审中 / 完成」，按里程碑（M0–M6）字段分组；发现缺陷或需要讨论时才单独建 Issue。
- **标签**：`area/core`、`area/store`、`area/formats`、`area/games`、`area/ui`、`area/meta`、`area/ci`；`game/<游戏>`；`priority/P0–P2`；`size/S–L`。
- **提交信息**：遵循 Conventional Commits（`feat:`、`fix:`、`docs:` 等），便于生成更新日志。
- **文档入库**：功能需求、SRS、UI/UX、架构、开发计划导出为 Markdown 放入 `docs/`，原型 HTML 放入 `docs/prototype/`；之后以仓库里的版本为准。
